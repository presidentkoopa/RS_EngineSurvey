### B.2 Timing: what is stale, by how much

- **World time vs head time.** The world is interpolated for the loop-top instant (step 1); the head for `predictedDisplayTime` (step 7). The gap is tic-or-spin + `xrWaitFrame` + build + runtime lead. `r_ticstability` exists precisely to keep loop-top spacing even ("Forces playsim processing time to be consistent across frames", d_net.cpp:2245-2249): it pads tic-less frames by the tic's cost so the gap is constant. Inference: turning F12 off in VR without P2-10a reintroduces jitter in that gap equal to the tic cost (no-mod ≈5 ms: ≈0.45 of a 90 Hz frame), which shows as actor judder. So P0-F12 and P2-10a are one change in VR. Stock 5.0 has the same spin ([U] src/d_net.cpp:2102-2122, call :2275); the fork did not change it.
- **Gameplay hand pose.** `WriteHandCommand` (VK-XR:8317-8365) reads `weaponoffset/weaponangles/hmdPosition/doomYaw/snapTurn` left by SetUp #2 of the previous frame, located at that frame's predicted display time. The command then waits for its tic (0-28.6 ms) and the result is shown one tic interpolated later. Drawn hands use this frame's SetUp #2 (r_data/models.cpp, `GetGripTransform`). Inference: gameplay aim lags the drawn hand by one frame plus the tic phase (11-40 ms at 90 Hz).
- **SetUp #1 hands** are located at the previous frame's predicted time (VK-XR:3913, 4158, 4362 before :6051): whatever SetUp #1 publishes (pawn fields in SP, haptics, wheel hover, `FVRRig` recompute keyed on `xrVRFrameIndex`, r_data/vr_rig.cpp:607-639) is one frame period stale (11.1 ms at 90 Hz) until SetUp #2 overwrites it.
- **No late latch.** One `xrLocateViews` per frame (VK-XR:6087); the same poses are submitted (VK-XR:6399-6410). Head-to-photon therefore includes the whole CPU build and GPU frame; the compositor reprojects rotation only, and no depth is submitted (P2-9c) for positional correction.
- **Refresh rate.** `ApplyRefreshRate` asks `XR_FB_display_refresh_rate` for `vid_refreshrate` once at session begin (VK-XR:5915-5992, 6029-6031). 90 Hz depends on VDXR offering it.

### B.4 Multiview: what exists and what is wrong with it

- Gate: cvar (hw_vrmodes.cpp:643, default false, "experimental") ∧ device probe `xrMultiviewSupported` (VK-XR:8596-8605) ∧ render mode GameplayEyes/MenuOverWorld ∧ 2 views (VK-XR:8608-8616). `BeginFrame` sizes layered buffers from SetUp #1's mode (vk_renderdevice.cpp:1489-1499); the eye loop decides from SetUp #2's (hw_entrypoint.cpp:354). A mode change between the two gives one inconsistent frame (survey 07 §1.3, Inference).
- Scene: built **once from eye 0's shifted position and eye 0's FOV** (hw_entrypoint.cpp:451-482), uploaded as two viewpoints (`ApplyMultiviewViewpoints`, :472). No cyclops, no combined frustum, no second clipper (P2-3/4/5). Inference: on runtimes with asymmetric per-eye FOV the clipper's symmetric `max(h,v)` window (VK-XR:1942-1949), centred on the left eye, can miss the right eye's outer edge; settle with the eyeshot diff (D4).
- Post-process: eye 1 runs the whole chain again on its layer (hw_entrypoint.cpp:385-407); only the scene→PP transfer is skipped for layer 1 (vk_postprocess.cpp:136-147); PP pass keys force `ViewMask = 0` (vk_pprenderstate.cpp:112, 159).
- Shaders: `GL_EXT_multiview` injected (vk_shader.cpp:1285), `main.vp` exports `gl_ViewIndex` (wadsrc/static/shaders/glsl/main.vp:57). [FR]'s level mesh shader is multiview-ready too ([FR] wadsrc/static/shaders/glsl/levelmesh.vp:118), but [FR]'s static walls/flats are drawn inside `RenderScene` ([FR] src/rendering/hwrenderer/scene/hw_drawinfo.cpp:3829-3835), so they are still per eye unless multiview is on.
- Billboards are eye-aware (`HWBillboard_SetEye`, hw_entrypoint.cpp:374-377); shared marches use `CentreViewPos` (hw_drawinfo.cpp:1448, 1652). Everything else that the playbook says must be cyclops (rotation frame, translucent sort, slope facing, render hacks) is decided from eye 0 in multiview and per eye otherwise.
- Avatar lane note: under multiview the model draw path runs once for both views. `FVRRig::Get` is keyed per frame (vr_rig.cpp:607-639), so the pose is shared, but the lane rule ("once per view, per frame", RENDER_LANE_HANDOFF_2026-11-09.md §1) must be re-agreed.

### B.5 Threads today

Main thread runs every tic, all ZScript, prediction, `NetUpdate`, sound update, GC, BSP traversal in VR, all command recording, every fence wait and every OpenXR call (d_main.cpp:1985-2018). ### C.2 What this area must deliver, and the gap

- **Frame-loop overhead outside scene and GPU ≤ 0.6 ms per frame** (steps 0-3, 8-10). Today: spin 2.7-3.2 ms average (no-mod) or the whole tic, polled waits 2-4 ms, double SetUp 0.1-0.5 ms → gap ≈ **5-8 ms per frame** on the no-mod case. Rows P0-F12, F-XR-2, P2-9a/b/d, F-XR-1 close it; all are determinism-neutral.
- **One scene build per frame** (P2-3..8): saves 3.5-4.2 ms of CPU against today's two builds.
- **Overlap**: frames in flight + `xrWaitFrame(N+1)` after submit N (P2-10b) turns `CPU + GPU` into `max(CPU, GPU)`; on no-mod that is up to 3.2 ms (the measured flat GPU wait).
- **Sim off the frame** (P8): turns the playsim requirement from "tic + render ≤ 9.6 ms on every tic frame" (tic ≤ ~3 ms with a 6 ms render) into "tic ≤ ~22 ms on its own core". For the modlist that is the difference between a 48× sim speed-up (144.7 → 3 ms) and a 6.6× one (144.7 → 22 ms). The 6.6× is owed by the playsim areas (thinker/helper-actor work); this area cannot shrink it, only stop it from landing in the headset frame.
- **Plan of record (structural) vs stopgaps.** The owner wants permanent fixes, so the plan of record for this area is three structural pieces: **(i) a rebuilt XR frame loop**: `xrWaitFrame` first, engine time = converted `predictedDisplayTime` (P2-10a), one controller/pose sample per frame (F-XR-1), frames in flight with `xrWaitFrame(N+1)` after submit N (P2-10b), the final pass written into the XR swapchain with no CPU fence waits anywhere on the XR path (P2-9a/b/d, F-XR-2), late latch (P8-6), depth layer (P2-9c), HUD quad layer (P2-11); **(ii) one stereo scene build**: cyclops pose, combined frustum, dual clipper, cyclops decisions, multiview incl. layered PP (P2-3..8); **(iii) the sim thread on a render snapshot** (P8-1..7), which first needs every B.6 hazard closed so "the renderer may only draw" is true. In (i) `r_ticstability` is not tuned but removed from the VR path, because frame time no longer comes from the loop top. **Stopgaps**, worth shipping only because they are days of work and determinism-neutral, and to be deleted when the structure lands: the `TicStabilityWait` VR guard alone, sliced fence waits on the old serial loop, `sim_maxcatchup` (made moot for SP by the sim thread's own pacing), `vr_scene_multithread 1`, `vid_vsync 0`/`vr_desktop_view -1` in the ini.
- **Sequencing that respects the lanes (Inference).** (1) Render lane on `renderer`, behind an off-by-default cvar (e.g. `vr_xrloop 1`): the rebuilt XR frame loop (i), which touches `D_DoomLoop`/`D_Display` (theirs), `I_SetFrameTime` and the view/swapchain half of VK-XR; its only change in `TryRunTics` (netplay lane's) is skipping the spin when the new loop is on.
