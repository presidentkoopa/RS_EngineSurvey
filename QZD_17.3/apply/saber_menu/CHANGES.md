## 0. FIRST: THE BLADE LENGTH. 100 cm does not exist.

You asked for **50, 75, 100, 125, 150**. Here is what the code can actually draw.

`ubqs_size` is **not continuous**. `ResolveSizeIdx()` (`zscript.txt:466-478`) snaps whatever you set
to the nearest of five baked scales, and there is no sixth:

```
static double Size(int s) { static const double T[] = { 0.70, 0.85, 1.00, 1.15, 1.30 }; return T[clamp(s, 0, 4)]; }
```
— `zscript.txt:30`

The blade is `26.0 * Size(...)` map units (`:851`), and a map unit is 1/34 m
(`vr_vunits_per_meter 34.0`, verified at `qzd173/…/hw_vrmodes.cpp:94`). So the five blades are:

| `ubqs_size` | map units | **real length** |
|---|---|---|
| 0.70 | 18.2 | **54 cm** |
| 0.85 | 22.1 | **65 cm** |
| 1.00 (today's default) | 26.0 | **76 cm** |
| 1.15 | 29.9 | **88 cm** |
| 1.30 | 33.8 | **99 cm** |

**99 cm is the longest blade this mod can draw.** If you meant centimetres, then 100, 125 and 150
do not exist, and a menu offering them would snap all three to the same 99 cm blade — you would
move the setting and see nothing change. If you meant percent, 50 and 75 both snap to 0.70 and 150
snaps to 1.30, so five entries would give three blades.

Either way, **your five values cannot all map to distinct blades today.** Three honest options:

**(a) Relabel the row to the five real lengths — `54 / 65 / 76 / 88 / 99 cm`.**
Zero cost, available now, nothing can be promised that is not delivered. **This is what the
`MENUDEF` in this folder ships.** What you lose: the longest blade stays 99 cm.

**(b) Extend the table to seven scales so 50-150 cm all exist.**
Cheap *in principle*. The only per-size difference in `MODELDEF` is the `Scale` line, and it is
exactly linear: `-1.126` at 0.70 (`MODELDEF:22`) against `-2.090` at 1.30 (`MODELDEF:9422`), ratio
1.856 against 1.30/0.70 = 1.857. **No new art.** 50/75/100/125/150 cm need `ubqs_size` of
0.654 / 0.98 / 1.31 / 1.63 / 1.96.
**BLOCKED.** `MODELDEF` is generated — its own header says so (`MODELDEF:2`, *"GENERATED by
ubqs.py"*) — and `tools/ubqs.py` is not in the repository. See Part C.

**(c) Ship (a) now, do (b) when the generator surfaces.**

**Recommendation: (c).** Take (a) today — it is in the `MENUDEF` here and costs nothing — and keep
(b) on the list for whenever `ubqs.py` turns up. The code does not argue otherwise: nothing else in
the mod assumes a particular number of sizes. `UBQS_Data.Size` clamps to `0..4` and
`ResolveSizeIdx` loops `i < 5`, so extending the table means touching those two literals and
nothing else in `zscript.txt`.

### A.1 Why deleting 112 cvars needs no code change

This is the part that makes Part A safe, and it is worth reading once.

`UBQS_Data.F` and `.I` return **the fallback the call site passes** when the name is not found:

```
static double F(Actor who, String n, double fb)
{
    CVar c = null;
    if (who && who.player) c = CVar.GetCVar(n, who.player);
    if (!c) c = CVar.FindCVar(n);
    return c ? c.GetFloat() : fb;
}
```
— `zscript.txt:191-197`, and `.I` identically at `:198-204`

So a deleted cvar silently adopts its in-code literal. I extracted all 119 reads that carry a
fallback literal and compared each against the old `CVARINFO` default. **118 of 119 match to the
digit.** The seven `ubqs_glow_*` prediction names fall back to the `GLOW_*` constants they were
made from — `GLOW_AGE 11.1`, `GLOW_MAXANG 35.0`, `GLOW_MAXLIN 4.0`, `GLOW_RAMPW 60.0`,
`GLOW_STOP 0.6`, `GLOW_FADEW0 200.0`, `GLOW_FADEW1 500.0` (`zscript.txt:1306-1321`) — which are
identical to their old defaults, so those deletions are no-ops by construction.

The 18 names read through `CVar.FindCVar` instead were each opened and read. All treat *absent* as
the old default:

| cvar | site | absent behaves as |
|---|---|---|
| `ubqs_bd_sword` | `:5523-5524` `return !bc \|\| bc.GetBool();` | true ✓ |
| `ubqs_chainsaw` | `:5529-5530` `return cc && cc.GetBool();` | false ✓ |
| `ubqs_hitscan_guard` | `:5630-5631` `if (hc && !hc.GetBool()) return false;` | guard on ✓ |
| `ubqs_doppler` | `:3148-3149`, `:3184-3185` `cv ? clamp(...) : 1.0` | 1.0 ✓ |
| `ubqs_force_hand` | `:5806-5810` `(!fhc \|\| fhc.GetBool())` | true ✓ |
| `ubqs_dual` | `:5541` (migration, `dc &&` → skipped) and `:5669-5670` `if (dc && !dc.GetBool())` | skipped ✓ |

**The one exception is `ubqs_haptic_clash`** — Part B edit 2.

### A.2 What the 11 rows are, and the two that are not yours

Nine are your draft, in your order, with your spacers. Two I argued for and you approved:
**Swing to Cut** and **Blade Block Reach**, in their own group at the bottom.

- **Swing to Cut** (`ubqs_swing_cut` 8.0) is the mod's own stated most-felt number
  (`zscript.txt:1225-1228`): *"what counts as a hard swing depends on arm length, standing or
  seated, and the size of the room. Every 'walking registers a swing' and every 'my slash did
  nothing' lands here."* 8 units a tic is 8.2 m/s of tip speed. No single value serves a seated and
  a standing player, and the failure is silent — the blade passes through the monster.
- **Blade Block Reach** (`ubqs_blade_guard` 6.0) is left to you in writing by
  `docs/HANDOFF_polish.md` (`agent-block`, "Not done / headset"), with the measurement: at 6 units,
  **22 of 364** Brutal Doom rifle tracers still got through.

**One range change to flag:** the Blade Block Reach slider runs **1-24, not 0-24.** `0` used to
mean "fall back to the old cone-and-percentage roll", and that roll is being retired (it was
unreachable at every non-zero value, i.e. at every value anyone has ever run — see §B.4). Offering
0 on the menu would be offering a path nobody has tested this decade.

### A.3 What the menu plumbing does, and that it is preserved byte-for-byte

I checked `zscript/ubqs_rsmenu.zs` before touching `MENUDEF`. The hook is three blocks and all
three are carried over unchanged:

1. `OptionMenu "RSQ_RSOptions" protected { Class "UBQS_RSMenu" … }` — the shared parent. It is
   **protected** so QZD 17.3 *merges* a later definition instead of replacing it
   (`ubqs_rsmenu.zs:6-10`), and a merge of zero rows changes nothing. Whichever series pk3 loads
   first creates it.
2. `AddOptionMenu "OptionsMenu" { UBQSRSLink "Radiant Silvergun Options", "RSQ_RSOptions" }` —
   `OptionMenuItemUBQSRSLink` (`ubqs_rsmenu.zs:20-47`) takes an `OptionMenuDescriptor` as its first
   `Init` argument, so the parser hands it the menu it is being added to and it unlinks any earlier
   copy of itself. That is what keeps Options showing **one** row however many series pk3s load.
3. `AddOptionMenu "RSQ_RSOptions" { Submenu "RSQ Saber", "UBQS_Options" }` — this mod's own row.

**Do not touch `zscript/ubqs_rsmenu.zs`.** Its own header (`:1-2`) says it is generated from
`tools/rsmenu/rsmenu_template.zs` and that a mod's copy must not be edited.
`OptionMenuItemUBQSPreset` (`:145`) becomes unused when the preset rows go — **leave the class
there.** It lives in the shared template and other series pk3s use it.

### A.4 One thing I am not deciding for you: how Damage reads

You drew **`Damage: sliderbar 0.5 - 2.0`**. `ubqs_damage` is **absolute** (30.0), and a GZDoom
`Slider` has no display scaling — it shows the cvar's own number. So:

- **What the `MENUDEF` here ships:** `Slider "Damage", "ubqs_damage", 15, 60, 3, 0` — sixteen
  notches from 15 to 60, which **is** 0.5× to 2.0× of 30, but the row reads *"Damage 30"* rather
  than *"Damage 1.0"*. Zero code change. Both endpoints verified safe: nothing clamps or divides by
  `ubqs_damage` at any of its three sites (`:1875`, `:2016`, `:4085`), and at 15 an imp still dies
  in 4 cuts ≈ 0.9 s at the 8-tic recut cap.
- **If you want it to literally read 0.5-2.0**, that needs a new `ubqs_dmg_scale` cvar and a
  multiply at those same three sites — i.e. a Part B edit, which the generator can revert.

**I am not picking for you.** The shipped version is the no-risk one; say the word and the
multiplier is three lines.

### B.1 REQUIRED — the off-hand light. Delete the 1.17 m merge.

**This is the mechanism behind your "Off Blade Light" row, and it is the bug you noticed.**
`HandPos()` returns `OffhandPos`/`AttackPos` raw (`:141-146`, `:825`), which the engine writes in
**map units** (`hw_openxrdevice.cpp:593`, `:606-607`) at 34 units per metre
(`hw_vrmodes.cpp:94`). So `40.0` is **1.176 m** — wider than hands ever are. The off blade has been
unlit in every normal dual-wield pose. (The Z term also carries `/ pixelstretch`,
`hw_openxrdevice.cpp:608`, so vertical separation reads 1.25× larger and escapes it even less.)

Recommendation: **delete the merge.** There is now an explicit switch, and two mechanisms answering
one question is the complaint in miniature.

**BEFORE — `zscript.txt:2843-2849`**
```
		int mode = on ? UInt("ubqs_lights", 1) : 0;
		int want = clamp(mode, 0, 3);
		if (want == 1 && bOffhandWeapon)
		{
			let o = Other();
			if (o && (o.HandPos() - HandPos()).Length() < 40.0) want = 0;
		}
```

**AFTER**
```
		int mode = on ? UInt("ubqs_lights", 1) : 0;
		int want = clamp(mode, 0, 3);
		// THE OFF BLADE'S LIGHT IS NOW A SWITCH, NOT A GUESS (ubqs_lights_offhand). This used to be
		// "when your two blades are close together only the main hand's lights them both", written as
		// 40.0 MAP UNITS -- and a map unit is 1/34 m (hw_vrmodes.cpp:94), so the cut-off was 1.17 m.
		// Hands are never that far apart, so the off blade was unlit in every normal dual-wield pose.
		// One answer instead of two: ubqs_lights sets the detail, this sets whether the off hand has one.
		if (bOffhandWeapon && !UInt("ubqs_lights_offhand", 1)) want = 0;
```

The comment two lines above, `:2838-2839`, still describes the deleted merge — fix it in the same
pass (it reads *"and when your two blades are close together only the main hand's lights them
both"*; that clause should go).

`Lights()` is already per-saber-instance (`:2841`), so this is the whole change.

### B.2 REQUIRED — `ubqs_haptic_clash`, the one fallback that does not match

`ubqs_haptic_cut` and `ubqs_haptic_clash` are being folded into `ubqs_haptics` (three switches for
one feature). `ubqs_haptic_cut`'s call site falls back to `1` (`:1878`), so deleting it means
"always on" — correct. **`ubqs_haptic_clash`'s falls back to `0` against a default of `1`**, so
deleting it would silently turn clash haptics **off**. This is the only such case in the file; I
checked all 119.

**BEFORE — `zscript.txt:2723`**
```
		bool buzzk = UInt("ubqs_haptic_clash", 0) != 0;
```

**AFTER**
```
		bool buzzk = true;   // the clash always buzzes; ubqs_haptics is the one switch (its own gate is in Rumble)
```

`Rumble()` still gates everything on `ubqs_haptics` (`:807`), so the master switch keeps working.

> **While you are in this function:** `ubqs_haptic_power` is fixed at 1.0 now, but the saturation
> is real and independent of this rework — `amp = clamp(k * 0.85, 0.12, 1.0)` at `:3238` means the
> clash's strength of 1.2 was already being clipped. `docs/HANDOFF_polish.md` lists it as known.
> Not fixed here; not made worse here.

### B.3 REQUIRED — decouple the combat flashes from the blade light

`ubqs_flash` is being fixed. Its fallback is `1`, and `1` means *"flashes only if the blade light
is on"* (`:2883`). The cvar exists **because that coupling was wrong** — `:2876-2880` says dropping
the light *"silently took the hit, block, deflect, clash, guard and burn flashes with it — the
player lost his combat FEEDBACK meaning only to lose the blade light."* Now that the off blade's
light can be switched off, `1` re-opens that trap. Fix at the equivalent of `2`: combat feedback
always.

**BEFORE — `zscript.txt:2881-2883`**
```
		int fl = UInt("ubqs_flash", 1);
		if (fl <= 0 || rad <= 0) return;
		if (fl == 1 && UInt("ubqs_lights", 1) <= 0) return;
```

**AFTER** — delete the third line only:
```
		int fl = UInt("ubqs_flash", 1);
		if (fl <= 0 || rad <= 0) return;
```

One line out. The hit, block, deflect, clash, guard and burn flashes now fire whatever the lights
are doing. **What you lose:** no way to turn the flashes off at all. That was never a row anyone
would have found, and it is the safer side of the trade.
